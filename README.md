# Marketplace API

Учебный сервис товаров и заказов на Kotlin и Spring Boot.

Контракт API хранится в OpenAPI. DTO и интерфейсы создаются при сборке.
Данные хранятся в PostgreSQL, изменения схемы выполняет Flyway.

## Запуск

Нужны Java 17 и PostgreSQL 17. На macOS PostgreSQL можно установить командой:

```sh
brew install postgresql@17
```

Скопировать настройки:

```sh
cp .env.example .env
```

В `.env` задать `DB_PASSWORD`, `SELLER_PASSWORD`, `ADMIN_PASSWORD` и `JWT_SECRET`.
Для JWT нужен случайный секрет длиной не менее 32 байт. Его можно получить через `openssl rand -base64 48`.
Пароли пользователей должны содержать от 8 до 72 символов и занимать не более 72 байт UTF-8.

Поднять локальную базу и загрузить настройки:

```sh
./scripts/db.sh
set -a
source .env
set +a
```

Скрипт создаёт отдельный кластер в `.local/pg` и базы `marketplace`, `marketplace_test` на порту 55432.
Путь к программам PostgreSQL можно задать переменной `PG_BIN`.
Миграции Flyway применяются при запуске приложения.

Создать продавца и администратора, затем запустить сервер:

```sh
./gradlew bootRun --args='--spring.profiles.active=seed --spring.main.web-application-type=none'
./gradlew bootRun
```

Сервер доступен по адресу `http://localhost:8080`.
Повторный запуск `seed` сохраняет пароли существующих пользователей.
Обычный пользователь создаётся через `POST /auth/register`.

Остановить базу:

```sh
./scripts/db.sh stop
```

## Сборка и тесты

Перед запуском команд загрузить переменные из `.env`, как показано выше.

```sh
./gradlew openApiGenerate
./gradlew clean build
java -jar build/libs/marketplace-api-0.1.0.jar
```

Генерация также запускается автоматически при сборке.
Тесты используют `TEST_DB_URL` и очищают только тестовую базу. Для неё нужна отдельная база `marketplace_test`.

## Правила заказов

Создание, изменение и отмена выполняются в транзакциях. Строки пользователей и товаров блокируются в одном порядке по UUID.
Частичный уникальный индекс допускает только один заказ пользователя в `CREATED` или `PAYMENT_PENDING`.

Состояния: `CREATED -> PAYMENT_PENDING -> PAID -> SHIPPED -> COMPLETED`.
Администратор переводит заказ в следующее состояние через `POST /orders/{id}/status`.
Отмена разрешена из `CREATED` и `PAYMENT_PENDING`.

При изменении состава старые позиции сохраняют цену заказа. Новые получают цену каталога.
Процентная скидка выше 70% равна нулю. Валидный промокод при этом расходует использование.
Фиксированная скидка не превышает сумму заказа. Округление скидки выполняется до копеек по `HALF_UP`.

Если при обновлении сумма стала ниже минимума промокода, он снимается и использование возвращается.
Истёкший или отключённый промокод вызывает полный откат обновления.
При отмене остатки и использование возвращаются один раз.

`ORDER_INTERVAL_MINUTES` задаёт интервал между успешными операциями. По умолчанию это одна минута.
Создание и изменение считаются отдельно для пользователя, выполняющего запрос. Значение `0` отключает интервал для локальной демонстрации.

## Авторизация

Вход возвращает access token на 15 минут и refresh token на 7 дней.
Защищённые запросы передают `Authorization: Bearer <access_token>`.
Refresh используется один раз; при обновлении выдаётся новая пара токенов.

USER читает каталог и управляет своими заказами. SELLER управляет своими товарами и создаёт промокоды.
ADMIN может управлять любыми товарами и заказами. При создании товара он может указать `seller_id` продавца или администратора.
Регистрация всегда создаёт USER.

## Демонстрация

В `requests.http` собраны запросы для HTTP Client в IDE. В `queries.sql` находятся запросы для просмотра таблиц.

1. Войти продавцом, создать товар и промокод.
2. Зарегистрировать пользователя, войти и создать заказ с промокодом.
3. Показать заказ, остаток товара, строки позиций и счётчик промокода через SELECT.
4. Изменить заказ и показать пересчёт. Отменить заказ и показать возврат остатка.
5. Повторить отмену, заказать неактивный товар, передать неверное количество и выполнить запрос от другого пользователя.
6. Войти администратором и пройти цепочку состояний нового заказа.

Каждый запрос записывается в JSON-лог. `X-Request-Id` связывает ответ с записью в логе; пароли и токены в теле маскируются.
